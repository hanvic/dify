## 1. 1차 BLOCKER/Major 반영 검증

### 지적 #1 (BLOCKER): 영구 이미지 스토리지 디스크 소진

**기획자 반영**: 
- §3 결정3에 "200KB 목표, max-long-side 2048px, quality 75→60 단계적" 추가
- §6 디스크 예산표 추가 (27,754×200KB = 5.4GB)
- 대안 전환 계획 3단계 제시

**리뷰어 재검증**:
```
$ df -g /System/Volumes/Data
Available: 14GB (PLAN은 16GB 기준 — 2GB 차이 발생)

$ python3 이미지 압축 실측 (5개 샘플 PDF):
  2048px/q60: 168~291KB, 평균 ~237KB
  2048px/q50: 152~261KB, 평균 ~213KB
  1536px/q75: ~204KB
```

**평가**: 
- 디스크 여유가 16GB→14GB로 감소 (STATE_BRIEF 작성 이후 변동). 7.1GB 잔여 추정치는 **5.1GB**로 하향.
- 2048px/q60 평균은 **237KB**로 200KB 목표 미달. `q50` 또는 `1536px/q75`가 필요.
- 그러나 핵심 구조(이미지 압축 + 체크포인트 + 대안 전환)는 적절. Phase 2 체크포인트에서 실측 → 보정 가능.

**판정**: ✅ **수용** (구현 중 확인 사항으로 강등)
- **구현 중 확인**: 디스크 14GB 기준으로 재계산 시 총 예산 = 14 - 2(안전여유) = 12GB 사용 가능. 이미지 5.4→6.6GB(237KB 평균), 벡터 1.7, PG 0.3, node_modules 1.5 = 합계 10.1GB. 여유 3.9GB. 가능하나 여유 작음.
- **권고**: compress 목표를 "평균 ≤250KB" 로 현실화하거나, Phase 1에서 실측 평균 기반 디스크 예산 재산출.

### 지적 #2 (Major): 속도 16.8s 가정 - 파이프라인 설정 변경 필요

**기획자 반영**: §4 Phase 0에 파이프라인 설정 변경 추가, §2.3에 현재/목표값 명시

**리뷰어 재검증**:
```
$ DB workflow graph → VLM OCR tool_configurations:
  enable_thinking: {"type": "constant", "value": false}
  include_summary: {"type": "constant", "value": false}
```

**놀라운 발견**: 파이프라인에서 `enable_thinking=false`, `include_summary=false`가 **이미 설정되어 있음**. 이전 STATE_BRIEF의 "40s/page" 관측은 **thinking+summary ON 조건이 아니었을 수 있음**. 

가능한 설명:
1. 이전 세션에서 설정이 이미 변경됨 (STATE_BRIEF 작성 후)
2. 또는 40s는 업로드+큐잉+VLM+임베딩 전체 파이프라인 시간 (VLM만 16.8s + 오버헤드 23s)

실측: 배치 로그에서 33문서/25분 = **45초/문서** (폴링 포함). VLM만 16.8s라면 오버헤드 ~28s (업로드 5s + 큐잉대기 10s + 임베딩 8s + 폴링 지연 5s).

**판정**: ✅ **수용** (이미 해결됨)
- Phase 0에서 "변경" 대신 "설정 확인" 작업으로 변경 권고. 이미 적용됨.
- **구현 중 확인**: 파일럿에서 전체 파이프라인 소요시간(E2E) 실측 필수. 16.8s는 VLM만의 시간이며, E2E는 ~45s 예상.

### 검증 D: Weaviate/PG 현재 크기

```
$ du -sh volumes/weaviate/ = 5.5MB (33문서 기준)
$ du -sh volumes/db/ = 90MB (전체 Dify DB)
```

**27,754문서 추정**:
- Weaviate: 5.5MB × (27,754/36) = ~4.2GB (PLAN 예측 1.7GB보다 큼!)
- 실제로는 5.5MB에 인덱스 메타데이터가 포함되므로 선형 비례 아님. 벡터만 계산하면:
  - 768차원 × 4바이트 × 27,754 × 4.73세그먼트/문서 ≈ 384MB (순수 벡터)
  - HNSW 인덱스 오버헤드 ~2~3× → 0.8~1.2GB
  - PLAN의 1.7GB는 보수적 추정으로 적절

---

### 검증 E: 이미지 압축 현실성

```
실측 결과 (5개 다양한 PDF 샘플):
  2048px/q60: 평균 237KB (범위 168~291KB)
  2048px/q50: 평균 213KB (범위 152~261KB)
  1536px/q75: 약 200KB
```

**평가**: PLAN의 "2048px, quality 75→60 단계적" 설정으로는 평균 237KB. "≤200KB" 목표 미달이나 margin은 작음.
- 27,754 × 237KB = 6.4GB (200KB 계획의 5.4GB 대비 +1GB)
- 14GB 여유에서: 6.4 + 1.7(벡터) + 0.3(PG) + 1.5(node_modules) = 9.9GB → 잔여 4.1GB

**결론**: 237KB 평균이어도 디스크 내 수용 가능. 단, PLAN의 "7.1GB 잔여" 추정은 낙관적이며 실제는 **4.1GB 잔여** 예상.

## 3. 잔여 이견 → 구현 중 확인 사항으로 강등

3회차 규칙에 따라 남은 이견을 blocker/major가 아닌 "구현 중 확인 사항"으로 강등합니다:

### 확인사항 1: 이미지 압축 목표 현실화
- PLAN의 "≤200KB" 목표는 2048px/q60에서 237KB 실측. 
- **권고**: 목표를 "평균 ≤250KB"로 상향하거나, quality 50 적용. 
- **Phase 1에서 결정**: 50페이지 실측 평균 기반으로 디스크 예산 재산출.

### 확인사항 2: E2E 파이프라인 시간 = VLM + 오버헤드
- VLM만 16.8s이나, E2E는 ~45s/문서 (업로드+큐잉+VLM+임베딩+폴링)
- 72h 계획에서 Pro 병렬 3기준: 27,754 × 45s / 3 = 116h (72h 미달)
- **그러나** 배치 스크립트v2에서 비동기 파이프라인 제출이면 병렬 처리 효율 ↑
- **Phase 1에서 결정**: 파일럿 실측 E2E 기준으로 일정 재조정.

### 확인사항 3: 디스크 잔여 추정치 보정
- PLAN: 16GB 기준 7.1GB 잔여
- 실측: 14GB 기준 4.1GB 잔여 (237KB 이미지 평균)
- **Phase 2 체크포인트**에서 4,700p 완료 후 실측 대비 판단. 대안 전환 계획 이미 수립됨.

### 확인사항 4: top_k 조정
- 현재 knowledge-index의 top_k=2는 27,754 문서 풀에서 부족
- Phase 1 완료 후 에이전트 앱 설정에서 top_k=10~20으로 변경 + 검색 QA

### 확인사항 5: kimi-k2.6:cloud vs kimi-k2.7-code:cloud
- `ollama list`에는 kimi-k2.7-code:cloud만 표시되나, `ollama show kimi-k2.6:cloud`는 정상 동작
- Cloud 모델은 pull 없이 사용 가능하므로 문제 없음
- 단, VLM OCR 도구의 기본 모델 설정이 kimi-k2.6:cloud를 참조하는지 확인 필요

### 확인사항 6: 기존 36문서 정합성
- 현재 36문서/170세그먼트 존재 (PLAN은 33/152 기준)
- 기존 데이터 삭제/유지 여부는 사용자 확인(U5) 대기 중
- 새 배치는 동일 dataset에 추가되므로 기존 데이터와 공존 가능

## 5. 대안 평가 (기획자 채택/비채택 검토)

### 대안A (2단계 인덱싱: 블록OCR 먼저 + VLM 선별)

**기획자 판단**: 부분 채택 — 블록OCR 폴백 게이트로 채택, 전체 1차 인덱싱은 미채택

**기획자 근거**: "파편 25.6자 블록은 의미 단위 아님"

**리뷰어 재검증**:
```
$ 페이지 평균 블록OCR 텍스트 합산: 642자 (블록 25.6자 × 약 25블록/페이지)
$ 100자 미만 페이지: 1,344개 (4.8%)
$ 10자 미만 빈 페이지: 189개 (0.7%)
```

**평가**: 페이지 단위로 concat하면 평균 642자 — 충분한 검색 가능 텍스트. "25.6자 블록이 의미 없다"는 개별 블록 기준이고, 페이지 concat 시 의미 있는 텍스트가 됨. 

**그러나** 기획자의 핵심 반박은 타당: 
1. 전체 블록OCR 인덱싱은 citation 이미지 미리보기 불가 (핵심 UX 목표 미충족)
2. VLM OCR 결과의 마크다운 구조화가 임베딩 품질에 기여

대안A 전체 채택 시: 시간 90% 절감이나 핵심 UX(이미지 미리보기) 불가.  
**결론**: 기획자의 부분 채택(폴백용) 판단 수용. §6 대안 전환 2차(디스크 부족 시 블록OCR 전환)로 포함된 것이 합리적.

## 7. 승인된 최종 실행 계획 요약

### 핵심 구조 승인
1. **PDF 처리**: 호스트 PyMuPDF (이미 설치됨) → 페이지별 JPEG 스트리밍 추출 → 업로드 → 즉시 삭제
2. **문서 단위**: 페이지 1장 = Dify 문서 1건 (citation 이미지 미리보기 지원)

4. **이미지 압축**: 2048px/q60 (실측 평균 ~237KB). 디스크 내 수용 가능.
5. **단계적 실행**: 파일럿 50p → 일반문서 4,700p → 전체 27,754p
6. **Idempotency**: jsonl + 서버측 2차 확인 + 100건 백업
7. **디스크 가드**: 500p마다 체크, 2GB 미만 자동 정지, Phase 2 후 대안 전환 판정
